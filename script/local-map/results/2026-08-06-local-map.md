# 외부 장소 검증 비동기 분리 측정 결과

## 측정 환경

| 항목 | 값 |
|---|---|
| source | `7f2f31d` + working tree, image tag `devlog8-async-20260806` |
| 애플리케이션 | AWS ECS task 1개 |
| DB | MySQL 8.0, Hikari maximum pool size 5 |
| provider | 애플리케이션 내부 `STUB`, 고정 지연 300ms, 실제 네이버 API 호출 없음 |
| 부하 | k6 `constant-arrival-rate`, 후보 RPS당 30초, 최종 후보 3회 반복 |
| SLO | 쓰기 API p99 < 1,000ms, 성공률 >= 99%, dropped iteration = 0 |
| V2 추가 게이트 | 저장 수 + 준비 호출 1건만큼 provider 호출이 30초 안에 관측돼야 함 |

## 비교 구조

- V1: 게시글 트랜잭션 안에서 provider 재검색 300ms를 기다린 뒤 Post, Place와 PostPlace 저장
- V2: Post와 PostMeta를 먼저 커밋하고 `AFTER_COMMIT + @Async` 이벤트에서 provider 검증, 별도 짧은 트랜잭션으로 Place와 PostPlace 저장

V2는 API 응답만 빠르고 비동기 작업이 밀린 상태를 통과로 보지 않았다. 응답 SLO와 함께 provider 호출 완료 수를 확인했다.

## 최종 결과

각 버전의 최종 후보를 30초씩 3회 실행했다. 아래 API 지연은 반복별 p99의 중앙값에 해당하는 실행을 대표값으로 사용했다.

| 지표 | V1 15 RPS | V2 103 RPS | 변화 |
|---|---:|---:|---:|
| 검증된 최대 지속 RPS | 15 | 103 | 6.87배 |
| 쓰기 API 평균 | 359.20ms | 28.10ms | 92.2% 감소 |
| 쓰기 API p95 | 418.78ms | 33.16ms | 92.1% 감소 |
| 쓰기 API p99 | 426.25ms | 43.98ms | 89.7% 감소 |
| DB 트랜잭션 평균 | 338.40ms | 16.41ms | 95.2% 감소 |
| DB 트랜잭션 p99 | 357.41ms | 31.26ms | 91.3% 감소 |
| Hikari active 최대 | 5 | 3 | V2가 더 높은 부하에서 더 낮음 |
| Hikari pending 최대 | 0 | 0 | Prometheus scrape 기준 |
| 성공률 | 100.00% | 100.00% | 동일 |
| dropped iteration | 0 | 0 | 동일 |

V1 반복별 p99:

```text
426.25ms / 367.93ms / 508.93ms
```

V2 반복별 p99:

```text
590.52ms / 43.98ms / 40.76ms
```

V2 대표 구간의 비동기 provider 단계는 평균 300.19ms, p99 357.02ms였다. 외부 대기는 그대로 존재하지만 게시글 트랜잭션 밖에서 실행돼 API 응답과 DB 커넥션 점유 시간에 직접 더해지지 않았다.

## 인접 실패점

### V1 16 RPS

| 지표 | 값 |
|---|---:|
| API 평균 | 1,176.93ms |
| API p95 | 1,691.57ms |
| API p99 | 1,766.93ms |
| 성공률 | 100.00% |
| dropped iteration | 8 |

5개 DB 커넥션이 300ms provider 대기까지 포함해 점유되면서 15→16 RPS의 작은 증가에도 대기열이 누적됐다. p99와 dropped 조건을 모두 위반했으므로 15 RPS를 채택했다.

### V2 104 RPS

| 지표 | 값 |
|---|---:|
| API 평균 | 27.97ms |
| API p95 | 32.82ms |
| API p99 | 49.67ms |
| 성공률 / dropped | 100.00% / 0 |
| 기대 provider 호출 | 3,122 |
| 관측 provider 호출 | 3,109 |
| 30초 내 미도달 | 13 |

API SLO만 보면 통과지만 비동기 작업 13건이 provider까지 도달하지 않았다. 인메모리 executor의 포화 구간으로 판단해 104 RPS를 탈락시켰다. 따라서 이 환경의 최종 채택값은 비동기 완료까지 3회 검증된 103 RPS다.

## 정합성 게이트

| 확인 항목 | 결과 |
|---|---|
| 변조된 selection token | 저장 거부 |
| 같은 requestId 동시 재시도 | 10/10 성공, 한 게시글로 수렴 |
| provider 모드 | `STUB` 확인 |
| 실제 네이버 호출 | 0건 |
| V2 최종 103 RPS | 세 반복 모두 provider 호출 완료 확인 |

`@Async + @TransactionalEventListener`는 외부 호출을 DB 트랜잭션에서 분리하지만 전달 내구성을 보장하지 않는다. 운영에서 장소 보강 작업의 최종 전달이 필요하면 Transactional Outbox, 재시도와 DLQ가 후속 과제다.
